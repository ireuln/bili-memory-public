# 数据与内容层

> 一份归档 = **原始数据**（采到的事实）+ **派生数据**（从原始数据重算的视图）+ **可选内容层**（字幕、画面、结论）。
> 本文讲目录长什么样、字段怎么用、增量怎么写、备份怎么落地。**字段级契约只在 [`数据契约.md`](数据契约.md) 维护**，这里不再抄第二份表格。
> 怎么用见 [`使用指南.md`](使用指南.md)、[`../README.md`](../README.md)，出问题见 [`运维与排障.md`](运维与排障.md)，写入边界见 [`安全与边界.md`](安全与边界.md)。

## 1. 目录总览

`DataRoot` 与各级子目录名、主文件名都由 `config.json` 给出（`DataRoot`、`Dirs.*`、`MasterFile`、`HeatFile`、`ProgressFile`），**不要硬编码**。下表用占位符，`<...>` 一律指配置项。

| 位置 | 类别 | 内容 | 可重建 |
|---|---|---|---|
| `<DataRoot>/<History>/YYYY-MM.jsonl` | 原始 | 观看记录，按月分文件，一行一条，只追加 | ❌ 接口只回最近约 1200 条 |
| `<DataRoot>/<Fav>/<masterFile>` | 原始 | 收藏总表，一行一条，每次全量重写 | ❌ |
| `<DataRoot>/content/<BV>/` | 原始·可选 | 内容层：字幕、弹幕摘要、九宫格、结论 | ❌ 视频失效后再也取不到 |
| `<DataRoot>/<Heat>/<heatFile>` | 派生·补不回 | 热度时间序列，一天一条 | ❌ 历史播放量没有接口 |
| `<DataRoot>/<Detail>/<detailFile>` | 派生 | `-Enrich` 补的详情，一条一行 | ✅ 慢，有配额 |
| `<DataRoot>/<Fav>/*.md` | 派生 | 给人看的收藏可读表 | ✅ |
| `<DataRoot>/<History>/state.json` | 状态 | 观看游标，勿手改 | ✅ 代价是重扫 |
| `<DataRoot>/<Fav>/<progressFile>` | 状态 | 收藏断点，勿手改 | ✅ |
| `<DataRoot>/last-result.json` | 派生 | 最近一次采集的机器可读结果 | ✅ 下次运行覆盖 |
| `<ProjectRoot>/status.json` | 派生 | 给托盘/守护进程看的状态 | ✅ |
| 备份目录 `bili-archive-*.7z` | 副本 | 归档打包，见 §4 | — |

真正需要守住的只有前三行。其余都能重算，删了不心疼。

`DataRoot/登录态/` 虽然也在 `DataRoot` 下，但**不算归档数据**：它等价于账号，不进备份包、不拷贝、不上传。

## 2. 文件契约

一条总规则：**读取方认文件、先读 `schema`，不要解析控制台输出。** 当前契约版本 `1`，只增字段不改语义，未知字段忽略即可。完整字段表、单位、可空性一律看 [`数据契约.md`](数据契约.md)。

### 2.1 主数据

| 文件 | 用途 | 关键字段 |
|---|---|---|
| 观看记录 `YYYY-MM.jsonl` | 看过什么、什么时候看 | `view_at`（Unix 秒）、`bvid` / `aid`、`title` |
| 收藏总表 `<masterFile>` | 收藏了什么、何时失效 | `bvid`、`folder`、`attr`、`invalid`、`invalid_since`、`cover` |

四个坑（契约里有原文）：`duration` 不是观看时长；`is_finish` 已废弃、改用 `completion`；数组不按时间排序；总表**按视频去重**，同一视频只留最后一次出现的 `folder`。

### 2.2 状态文件

- `state.json`：`lastViewAt`（游标）、`lastRun`、`total`、`mid`。只由采集器读写，损坏时采集器记一条 WARN 并从零开始。
- `<progressFile>`：按夹记录收藏进度。**每跑完一个夹就落盘**，12 小时内已完成的夹自动跳过。两个文件都别手改。

### 2.3 派生文件

| 文件 | 用途 | 关键字段 |
|---|---|---|
| `<heatFile>` | 播放/弹幕/收藏数的时间序列 | `bvid`、`date`、`ts`、`view`、`danmaku`、`fav`、`source` |
| `<detailFile>` | 简介全文、源分辨率、自动识曲 | `bvid`、`desc`、`width`/`height`、`song`、`enriched_at` |
| `last-result.json` | 一次运行的结论，替代解析 stdout | `schema`、`mode`、`exit`、`finished`、`written` |
| `status.json` | 任务是否在跑、上次成败 | 只看不改 |
| `<Fav>/*.md` | 给人翻的收藏清单 | 不供程序解析 |

### 2.4 内容层（可选）

`<DataRoot>/content/<BV>/`，目录名就是 BV 号（大小写敏感），只用 ASCII，不带中文和空格。目录内五种文件，缺哪个都不算错：

| 文件 | 用途 |
|---|---|
| `meta.json` | 抓取时的元数据快照，`schema`、`bvid`、`title`、`up`、`duration`、`captured_at`、`source` |
| `subtitle.txt` | 字幕原文，每行 `[HH:MM:SS] 文本`，UTF-8 无 BOM；没有就别建 |
| `danmaku-summary.json` | 弹幕热区摘要（`total`、`per_minute`、最多 20 条 `hot`），**不存全量 XML** |
| `sheet.jpg` | 画面九宫格/时间轴图，JPG |
| `notes.json` | 评分（0–20，不知道写 `null`）与一句话结论，`by` 记 `human` / `ai` / `mixed` |

- 不存全量的理由很实际：一小时视频的弹幕 XML 常有 5–10 MB，信息密度却极低。
- **不设体积上限、不自动删除** —— 这是整份归档里唯一无法重新采集的部分。三处只报事实：`report.ps1`、`selftest.ps1`、`query.ps1 -ContentStats`。
- 查询侧：`query.ps1 -WithContent` 每条多一个 `has_content`；`-ContentStats` 给条目数/体积/时间范围，`level` 为 `ok` / `notice`（≥1 GB）/ `warn`（≥5 GB）。不加开关时输出与没有这一层时逐字节一致。
- 本仓库**只定义格式与读法**：不下载视频、不抓字幕弹幕、不校验内容真伪。写入方自己选工具。
- 经验值：只给深读过的视频建目录，图用 JPG、不存 mp4，一天 3 条约每天 1 MB 以内。
- 隐私：内容层文本比标题敏感得多，不进分享载荷、不进任何导出，只随加密备份走。

## 3. 增量与去重

一句话：**观看走游标、收藏走全量、热度按天覆盖、详情按轮转**。

### 观看记录（增量 + 跨次去重）

- 游标是 `state.json` 里的 `lastViewAt`；接口只回最近约 1200 条，所以必须每天增量，正常一天 35–45 秒。
- 游标**故意往前重叠几分钟**：卡在边界那一秒的两条不会漏。
- 去重键 `view_at|bvid`（没有 BV 用 `aid`，再没有用标题），并且**对磁盘上已有的键集去重**，不只对本次批次 —— 重叠的代价因此为零。
- 按 `yyyy-MM` 分组追加到对应月文件，不重写历史。
- `-Full` 忽略游标，从最近往回回填到 `-MaxPages`。

### 收藏总表（全量 + 断点）

- 每次全量拉一遍再整表重写，不做增量合并；去重键是 `bvid`，同一视频只留最后一次出现的 `folder`。
- 断点续跑：按夹落盘、12 小时内跳过已完成的夹。全量约 20 分钟，`-FavCheck` 不下载封面可省一半。

### 失效检测

- 判定依据是响应里的属性位：`attr & 1` 通常表示失效。命中后写 `invalid: true`，并把**首次观察到失效的时间**写进 `invalid_since`。
- `invalid_since` 是观测时间，不是平台判定时间，精度取决于采集频率。
- 失效后：不再更新封面（已存封面文件保留）、不写热度快照、`-Enrich` 跳过。
- 失效判断跟着收藏采集一起做，没有更快的旁路：一次全量约 20 分钟 / 22 个夹。
- 实测一份约 1.4 万条的收藏里约 15% 已经失效 —— 这正是"趁能取的时候存到本地"的理由。

### 热度与详情

- 热度去重键 `(bvid, date)`：同一天重跑只覆盖当天那一条（数值只会往前涨），换一天才追加。
- 热度文件**原子替换**写入（先写 `.tmp` 再换名），断电不会留下半行；`HeatMaxRows`（默认 5000）限制单次新增条数。
- 详情按 `bvid` 合并去重；`EnrichMax` 默认 300 条/次、间隔 600 ms，队列按 `enriched_at` 轮转（没补过的优先），所以不需要游标，也不会永远只补同一批。
- 详情走公开接口、不带登录态；会员/私享视频失败只记 WARN，下次轮转再试。

## 4. 备份到别处

备份包就是普通 `.7z`（或 `.zip`），不绑定本项目：卸掉工具后任何能读 7z/zip 的软件都能打开。

### 4.1 落到哪

- `ColdBackup` 是主落点，`BackupTargets` 里每一项各写一份（默认一块数据盘 + 一个云同步目录）。
- **同卷用硬链接**，两份只占一份空间；跨卷退化成真拷贝，这是预期行为，不是 bug。
- 文件名 `bili-archive-YYYYMMDD-HHMM.7z`；没有 7-Zip 时回退 `.zip`（不能加密），要兼容国产压缩软件可显式 `-Format zip`。
- 内容指纹没变就**不重新打包**（主落点下的 `.last-fingerprint`），避免每次生成几乎相同的包。

### 4.2 包内结构

| 路径 | 内容 |
|---|---|
| `bili/history/` | 观看记录 `*.jsonl` + `state.json` |
| `bili/favorites/` | 收藏总表、可读表 `*.md`、断点进度 |
| `collector/` | 采集脚本、`config.json` 等运行所需文件 |
| `MANIFEST.json` | 每个文件的 `path` / `bytes` / `sha256` |

登录态不进包 —— 它等价于账号，别为了"省一次扫码"把它塞进去。

### 4.3 是否加密

- **默认不加密**：包里是完整观看史，谁拿到谁能看。开箱即用，代价是明文。
- `-Encrypt` → 7z **AES-256 + `-mhe=on`**（文件名也加密）；必须有 7-Zip，`.zip` 做不到。
- 密码只存在本地 `backup-secret.json`，**该文件绝不跟包一起同步**，否则加密等于没有。
- 放网盘、共享目录、移动硬盘之前的最低要求，见 [`../SECURITY.md`](../SECURITY.md) 与 [`安全与边界.md`](安全与边界.md)。

### 4.4 保留份数与校验

- 默认保留 **5** 份（`-Keep`），超出删最旧；只删自己生成的 `bili-archive-*.7z|zip`，不动目录里的其他文件。
- 保留策略**只在本机生效**：云端/远端的旧副本要自己清，否则半年后就是一排包。
- 校验落点：`.\backup-package.ps1 -Verify` 列出每个目标的实际路径与可写性，**不写任何文件**。改完 `config.json` 先跑它，再动计划任务。
- 校验内容：不解压也能读 `MANIFEST.json` 的 `bytes` / `sha256`（包内清单在打包时生成）。
- 传输：让同步工具盯目录（Syncthing、网盘客户端）最省事；WebDAV/S3 用 `rclone copy <备份目录> <远端>:bili --include "bili-archive-*.7z"`。
- **备份失败就别上传**，否则同步上去的是半截包；判断依据看退出码或 `last-result.json`。
- 没有内置"备份完自动执行"的 hook，这是有意的：配置文件里能执行任意命令，等于把配置变成执行入口。要串动作就在调度层包一层脚本，接口形态见 [`自动化接口.md`](自动化接口.md)。
- 恢复演练与"只留备份、不留数据"的取舍见 [`使用指南.md`](使用指南.md)；当前进度见 [`计划与状态.md`](计划与状态.md)。
